## Wallet rules
- Wallet passes are issued only by `/api/wallet/$kind/$id` and `/api/wallet/google` from public profile/event data; profile cards (Google, Apple, 3D viewer) all come from `generateWalletPayload` → pure `walletCardPayload` in `wallet-pass.ts`, which also resolves both certificate naming schemes. A wallet with incomplete certificates is off and returns an unsigned demo payload. Why: private profiles never become passes, every surface shows the same QR, and missing keys never crash the share menu.
- The 3D ROUT Card (`components/wallet/RoutCard3D.tsx`) is lazy-loaded inside a dialog and falls back to the CSS card drawn from the same canvas faces when WebGL is missing or crashes. Why: three.js never enters SSR or the first page load.
- Card numbers (sovereign IDs) are HMAC(WALLET_ID_SECRET) over space + account id, falling back to a hash of public handle data only. Why: a card must never reveal or be derivable from the internal account id, and root/alias cards must stay unlinkable.
- Pass serials derive one-way from the card digest, never from the handle; public wallet endpoints accept handles only, account ids only via server code passing `allowAccountId`. Why: renaming a handle must not orphan saved passes, and account ids must not be probeable.
- The back-of-card secure QR is `/verify/<token>` from `card-token.ts`, built only for the signed-in owner from the 30 s liveness code and checked server-side (rate limited, one window of skew). Why: a photographed or recorded QR expires within a minute and cannot be forged without the server key.
